The Problem

📋
Static plans
Built once, never adjusted. A missed Monday stays missed forever.
🚫
No context

"John didn't fail. The app did."

The Most Important Thing I Built

Not a feature. A finding.

🐛 Discovered Day 13
My KB retrieval had been silently broken for 13 days. A SQL parameter-ordering bug caused every query to return [kb:error] and fall back to web search. Every eval score looked fine — because the answers were still coherent, just grounded in the wrong source. I found it by reading the retrieved data, not trusting the number.
📊 Honest result
After fixing the bug and re-running the ablation honestly: dense-only retrieval outperformed hybrid RRF on 4 of 5 metrics. I reported the reversal. The original "hybrid beats dense by 50%" claim was noise from a shared failure mode. That's the real result.

Eval scores measure coherence, not correctness of source. Spot-check raw retrieved content — don't trust the aggregate metric alone.

What I Found Building This

Five times the AI sounded confident but wasn't grounded

Calendar fabrication
The app invented "work travel Thursday–Friday" for a user who never mentioned travel. The mock calendar was injected as fact. Fixed: Scheduler only acts on what the user explicitly stated.
Weight question was decorative
Asked "what's your weight?" then immediately generated a plan without waiting. Fixed: a hard graph gate — no plan until weight is answered or declined.
Silent reply overwrite
Specific results (which day changed, memory citations) were computed correctly, then hidden behind a generic "take a look below." Fixed: diff-based reply composition — the reply now names exactly what changed.
Daily macro guesswork
After logging a meal, "remaining for the day" was LLM estimation, not real logged data. The food was in the database. The read path simply didn't exist. Fixed: get_daily_totals() + prompt injection.

Every fix had the same shape: stop letting the model claim what it should be retrieving or computing.
